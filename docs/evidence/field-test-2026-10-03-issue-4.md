# Issue 4 — mobile check-in keyboard viewport

Candidate: `fix/mobile-keyboard-dialog`, based on live `00c11695b2a33262589c0a4c7abaf3ab83848c86`. Changes are uncommitted; no deployment or live data access.

## Findings and change

The supplied iPhone screenshots show the long Add & Check In vehicle form moving when Make receives focus, with the action row competing with the keyboard accessory bar. Input zoom is already prevented: the mobile stylesheet sets editable controls to 16px. The existing visualViewport hook already debounces keyboard animation and avoids scrolling on each keystroke; those safeguards remain.

Two application layout choices contribute to the cramped typing area. Mobile dialogs were content-sized, bottom-anchored with an inset derived from `innerHeight`, `visualViewport.height` and `offsetTop`, and capped at 90% of the visible height. That leaves part of the scarce visible viewport unused and makes the sheet's upper edge depend on both content size and browser panning. More directly, the focus-reveal code reserved a fixed 64px while the sticky action footer plus sheet padding can exceed that, allowing a revealed input to remain behind actions.

The keyboard-open mobile sheet now occupies the measured visual viewport, with explicit `top: offsetTop` and `height/max-height: visualViewport.height`. It restores its normal bottom-sheet size when the keyboard closes. Focus reveal reserves the measured sticky footer height, actual bottom padding, and 12px of clearance. Dialog markup, native modal focus behavior, zoom handling, typing debounce, and desktop positioning are preserved. Only shared viewport/CSS code changes; vehicle selection, role controls and capacity wording are outside this patch.

The viewport distinction is documented by [MDN's VisualViewport API](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport): an on-screen keyboard may shrink the visual viewport without shrinking the layout viewport. [offsetTop](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport/offsetTop) describes the visual viewport's offset from the layout viewport. This supports using the measured visible rectangle directly. It does not prove every Safari keyboard version behaves identically.

## Validation

- Four hook tests pass, including obscured-field reveal, keyboard-animation debounce, no recentering during typing/panning, and a new wrapped 108px footer plus 24px padding case.
- TypeScript `tsc -b` passes; `git diff --check` passes.
- Four isolated Playwright checks pass in Chromium and WebKit: phone visual viewport shrink/pan, focused Make input above the action row, retained text/focus, 16px input size, keyboard dismissal restoring ordinary sheet size, and desktop dialog size/focus.
- Browser tests use the actual shared React Dialog, viewport hook and stylesheet in a synthetic long vehicle-form fixture. They require no API/server/database fixture mutation. The WebKit dependencies are supplied by the existing local `aac-browser-tests:1.63` image.
